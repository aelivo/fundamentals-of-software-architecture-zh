# 第 3 章学习笔记

## 阅读范围

第三章全文，书内第 37–53 页，PDF 第 57–73 页。以下为学习整理，与译文正文分开。

## 核心理解

1. 模块化是逻辑组织原则，不必等同于文件、部署包或进程的物理分离。
2. 内聚关注哪些代码应该放在一起，耦合关注代码之间的依赖；拆分内聚模块可能增加耦合。
3. LCOM 只能提供结构信号，不能判断业务语义；指标需要解释。
4. 传入、传出耦合反映连接方向；共变性进一步区分双方为什么必须共同变化。
5. 共变性需要同时结合强度、局部性和影响范围分析。模块内部与跨模块边界的同类依赖，代价可能不同。
6. 静态代码分析仍不足以回答同步与异步通信等架构问题，后续章节将扩展讨论。

## 原文疑点与校订记录

- 已渲染检查公式所在的书内第 42、43、45、46 页，确保集合基数、求和、上下标和绝对值未因文字提取而丢失。
- 公式 3-1 下方 P、Q 的增减描述与公式的集合基数写法不协调。译文保留，并明确提醒不要直接据该段实现计算。
- 公式 3-3 将抽象制品与具体制品相除，但后面的 5,000 行代码示例混用计数口径，且后文主要将 A 视为 0 到 1 的值。保留本版原文，不擅自替换公式。
- 公式 3-5 保留为归一化指标 D = |A + I - 1|；不将其误当成未经归一化的欧氏垂直距离。
- 关于 Java 版本、包级初始化、JAR 和名称冲突的表述按原书翻译，未作为 Java 规范说明进行外部验证。
- 原文将部分指标归入特定指标集；学习实际工具时需核对工具与指标版本，不能假设名称相同就定义相同。
- CoT 同时用于类型共变性与时机共变性，依上下文区分。
- 原文 Jim Weirich 的 Rule of Degree 按原名译为“程度法则”，其内容谈的是将强共变性转换为弱共变性；保留这一原文用法。

## 项目练习

- 找一个工具类，观察方法是否围绕同一组字段或业务职责工作；说明是否值得拆分，以及拆分会引入什么依赖。
- 找一项跨模块约定，判断它属于名称、类型、含义、顺序还是运行时共变性；如何降低跨边界的协调成本？
- 用代码分析工具获得传入、传出依赖，再检查数据是否与自己的设计理解一致。
