# 第 20 章学习笔记

## 阅读范围

第二十章全文，书内第 297–314 页，PDF 第 317–334 页。以下为学习整理，不属于原书正文。

## 当前理解

- 风险矩阵把影响和发生可能性分别判断，再相乘；先讨论影响，再讨论可能性，可以减少混淆。
- 评分需要明确背景和维度。相同架构部位的性能风险与可用性风险，不能因为分数相同就合并讨论。
- 风险报告应按受众目的筛选，并显示变化趋势；只看一个时点的红黄绿，无法知道缓解措施是否有效。
- 风险风暴先让参与者独立识别，再共同达成共识、提出缓解方案。这能让不同经验和未知知识暴露出来。
- 降低风险有成本，需要讨论可接受的剩余风险。最昂贵、覆盖最全的方案不一定是业务能接受的选择。
- 示例依次拆分数据库、加入队列与缓存、拆分 API 网关；每个修改都对应先前确认的风险维度。
- 风险分析需要持续进行，尤其在重大功能、重构或迭代变化之后，而不是上线前只做一次。

## 联系自己的项目

1. 选择单个维度，例如可用性，先更新架构图，再让不同角色独立评分。
2. 记录分歧背后的证据，区分影响高、概率高和团队不熟悉技术这三种情况。
3. 为每项高风险写缓解成本、剩余风险、验证方式及复查时间，连接到 ADR 和适应度函数。
4. 为同一份风险数据准备整体视图、高风险视图和趋势视图，检查它们是否适合不同会议目的。

## 适用范围与待核对

- 评分使方法统一，但不把主观输入变成统计概率；风险分数求和是作者的相对比较方法，不是期望损失计算。
- “未知技术始终评 9”是作者的练习规则，不是对产品本身风险的实测结论。
- 原书护士诊断案例把 HIPAA 与“只有护士能访问病历”对应，译稿按案例设定保留并明确标注，未把它当成法规解释。
- SLA 并不直接证明所有风险消失；本章的合同、可用率与停机时长按示例保留，未核验现实服务。
- 排队可吸收速率差异，但不能单独提高后端服务能力；原文也指出等待时间问题。诊断缓存的有效性与边界在案例外仍需单独验证。
